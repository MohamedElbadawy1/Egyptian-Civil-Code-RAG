# 05 - Experiment Tracking (MLflow) & Data Versioning (DVC)

**Status:** Done - full pipeline run end-to-end on the real machine (`dvc
repro` + `dvc push` both succeeded, 2172 chunks re-indexed)
**Date:** 2026-09-27

## What we built
- **DVC** (`dvc.yaml`, `.dvc/config`, `data/raw/egyptian_civil_code.pdf.dvc`):
  - `data/raw/egyptian_civil_code.pdf` is DVC-tracked directly (a true
    source input, not generated by any stage).
  - `data/processed/civil_code_articles.json` is the output of the
    `build_corpus` pipeline stage, declared with `cache: false`: DVC
    records its hash in `dvc.lock` but does not store or gitignore it -
    git tracks the file itself (~1.2MB). See "Why" below.
  - Two pipeline stages: `build_corpus` (PDF -> JSON, depends on the raw
    PDF and `parse_pdf.py`) and `build_index` (JSON -> Weaviate, depends
    on the JSON and every `rag/*.py` module that affects what gets
    embedded).
  - Remote: a local folder (`../dvc-storage-egyptian-civil-code-rag`,
    sibling to the repo) - no cloud storage account needed for now.
- **MLflow**: `rag/pipeline.py`'s `index_corpus()` now wraps the indexing
  run in `mlflow.start_run()`, logging the embedding model name,
  dimensions, batch size, corpus path, article/chunk counts, and the
  final indexed-vector count.

## Why / decisions
- **The corpus JSON stays in git (`cache: false`), only the raw PDF is
  fully DVC-managed.** First version handed the JSON entirely to DVC
  (cached + gitignored). That broke something no test caught: the Docker
  image copies `data/processed/` at build time and the API reads the JSON
  at runtime, but CI can't `dvc pull` from a local-folder remote on a
  laptop - so the image built successfully in CI *without* the corpus and
  `/ask` would have failed. It went unnoticed locally because `docker
  build` copies from the working directory, where the file exists. Fix:
  `cache: false` on the output in `dvc.yaml` (git tracks the small file,
  `dvc.lock` still pins its hash, reproducibility is unchanged), and CI
  now runs the built image and asserts the corpus loads (>1000 articles)
  so this can't silently regress. Revisit if the corpus ever grows large
  or a cloud DVC remote (reachable from CI) is added.
- **`civil_code_articles.json` is a pipeline output, not a standalone
  `dvc add`.** Originally `dvc add`ed it directly, but that conflicts
  with also declaring it as `build_corpus`'s `outs:` in `dvc.yaml` (DVC
  refuses to track the same file two ways). Since the pipeline is the
  actual source of truth for how that file gets produced, removed the
  standalone `.dvc` file and let `dvc repro` own it via `dvc.lock`.
- **Root `.gitignore`'s old blanket `/data/raw/*` and `/data/processed/*`
  rules were removed.** They predated DVC and would have blocked the
  `.dvc` pointer files and DVC's own per-folder `.gitignore` entries from
  being git-tracked at all - the two mechanisms were fighting each other.
  DVC now owns ignoring the actual data files (via
  `data/raw/.gitignore`, auto-generated by `dvc add`), and git only sees
  the small pointer file. (`data/processed/.gitignore` was later removed
  when the JSON went back to git - see first bullet.)
- **`build_index` has no `outs:` in dvc.yaml.** Its output is Weaviate (an
  external service), not a local file DVC can hash - it's still a real
  pipeline stage that reruns when its deps change, just not a producer of
  a versioned artifact.
- **Local DVC remote, not cloud.** Simplest option requiring no
  account/credentials setup; trivial to point `dvc remote modify` at S3 /
  GDrive / etc. later without touching the pipeline itself.
- **MLflow tracks the indexing pipeline, not a traditional training
  run.** There's no model training in this project - what's worth
  comparing across runs is the embedding *configuration* (model,
  dimensions, batch size) and its effect on chunk/vector counts, so
  future changes (a different embedding model, the heading-tracker fix
  changing `embedding_text()` output) are traceable runs instead of only
  living in chat history and docs.

## How to run
```bash
# One-time: point DVC at your own local remote folder if you want a
# different location than the default in .dvc/config
dvc remote modify -d localstorage <your-path>

# Reproduce the pipeline (only reruns stages whose deps changed)
dvc repro

# Pull data from the remote on a fresh clone (or push after producing it)
dvc push
dvc pull

# View MLflow runs (after running the indexing stage at least once)
uv run mlflow ui
# then open http://127.0.0.1:5000
```

- Hit the expected friction along the way, all fixed:

    `data/processed/civil_code_articles.json` were still directly
    git-tracked from before DVC was introduced (Step 0/01), which DVC
    refuses to also track - fixed with `git rm -r --cached` on each,
    handing ownership to DVC
- With those fixed, `dvc repro` ran both stages clean: `build_corpus`
  reproduced the 1086-article JSON, `build_index` re-embedded and
  re-indexed all 2,172 chunks into Weaviate (same count as Step 02's
  manual run, now driven by the DVC-tracked pipeline instead of a bare
  script call) - `dvc.lock` updated for both stages.

## Known issues / next steps
- `dvc.yaml` commands are prefixed with `uv run` (learned the hard way in
  Step 03 - a bare `python`/`uvicorn` on this Windows setup can resolve to
  the wrong global Python instead of the project's `.venv`).
- MLflow's tracking URI isn't configured explicitly yet - on this
  Windows run it defaulted to a local SQLite database
  (`mlflow.store.db.utils: Creating initial MLflow database tables`)
  rather than the plain file-based `./mlruns` store seen in the earlier
  smoke test - fine for solo local use either way, but worth pinning
  explicitly if this ever needs to be consistent across machines.
- No MLflow run for `build_corpus` (the ingestion stage) - only
  `index_corpus` is instrumented. Could add if the ingestion side ever
  needs run-to-run comparison (e.g. tuning the heading-tracker regexes).
- `pdftotext` (Poppler) is a system dependency the Dockerfile/CI never
  needed (ingestion isn't part of the served image - see docs/04), but
  local dev on a fresh machine needs it installed separately for
  `dvc repro` to work - worth a line in the README's setup instructions.
